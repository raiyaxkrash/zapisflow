# Чек-лист безопасности и аудита платформы (Production Security Checklist)

Данный чек-лист содержит перечень обязательных проверок защищённости мультитенантной платформы Beauty Bot перед вводом в эксплуатацию.

---

## 1. Защита криптографических ключей и токенов
- [x] **Алгоритм шифрования:** Telegram-токены ботов шифруются алгоритмом AES-256-GCM с уникальным 96-битным nonce.
- [x] **Аутентифицированные данные (AAD):** В качестве AAD используется идентификатор бота (`telegram_bot_id`). Токен, зашифрованный для одного бота, невозможно подставить другому боту (cross-tenant substitution rejection).
- [x] **Очистка FSM в Redis:** Временные plaintext-токены удаляются из состояния FSM сразу после валидации и шифруются перед сохранением в постоянное хранилище.
- [x] **Маскирование в логах:** Реализован фильтр `SensitiveDataFilter`, маскирующий секреты в формате `123456789:***...***` во всех журналах приложения.
- [x] **Отсутствие токенов в URL:** Вебхуки используют непредсказуемый UUID `public_bot_id`, токен никогда не фигурирует в URI пути.

---

## 2. Безопасность Webhook Ingestion Engine
- [x] **Timing-Safe сравнение:** Секретные токены заголовка `X-Telegram-Bot-Api-Secret-Token` проверяются строго через `secrets.compare_digest`, исключая атаки по времени (Timing Attacks).
- [x] **Защита от отказа в обслуживании (DoS / OOM):** Потоковый ограничитель `read_limited_request_body` проверяет как заголовок `Content-Length`, так и входящие чанки потока, не позволяя забить RAM запросами с `Transfer-Encoding: chunked`.
- [x] **Идемпотентность и дедупликация:** Входящие `update_id` дедуплицируются атомарно в Redis с помощью `SET NX EX`.
- [x] **Санитизация Health Check:** Эндпоинт `/health/ready` возвращает стандартизированный статус `"error"` при сбоях БД/Redis, не раскрывая строки подключения и учётные данные.

---

## 3. Многотенантная изоляция (Multi-Tenancy & IDOR Prevention)
- [x] **Проверка владельца (Ownership Check):** Все операции в Manager Bot проверяют принадлежность проекта (`master.owner_user_id == user.id`).
- [x] **Изоляция бронирований и услуг:** Доступ к слотам, мастерам и расписанию строго изолирован по `master_id`.
- [x] **Ролевая модель:** Исключена глобальная модель администраторов, права администратора строго привязаны к конкретному мастеру (`MasterAdmin`).

---

## 4. Безопасность биллинга и подписок
- [x] **Блокировка ручного биллинга в продакшн:** При `APP_ENV=production` ручное самоподтверждение оплаты мастером заблокировано на уровне сервиса и скрыто из интерфейса.
- [x] **Защита от двойного списания / продления:** Метод `process_successful_payment` блокирует строку `Master` через `SELECT ... FOR UPDATE` и проверяет статус платежа `SUCCEEDED` для предотвращения параллельных продлений.
- [x] **Сохранение доступа при истечении тарифа:** При статусе `EXPIRED` вебхуки бота продолжают приниматься, данные не удаляются, мастер сохраняет доступ к CRM и панели управления.

---

## 5. Защита инфраструктуры и развёртывания
- [x] **Non-Root контейнеры:** Приложение в `Dockerfile` запускается от непривилегированного пользователя `appuser`.
- [x] **TLS/HTTPS:** Весь входящий трафик шифруется протоколами TLS 1.2 / TLS 1.3 с заголовком `Strict-Transport-Security`.
- [x] **Ограничение частоты (Rate Limiting):** На уровне Reverse Proxy настроен лимит 30 r/s на IP с burst до 50.
- [x] **Регламент резервного копирования:** Резервные копии PostgreSQL валидированы через `pg_dump -F c` и проверены утилитой `pg_restore`.
